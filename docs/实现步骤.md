# 重构实现步骤

按依赖推进：共享契约与状态规则 → 基础设施和表结构 → 最小入库与旧数据迁移 → Retrieval → Agent → 网关 → 前端 → 故障与回归验收。现有算法实现先保留，完成连接、权限和执行方式改造后再整理模块内部结构。

第一版使用 Compose 管理中间件，Python 服务在本机启动。网关和 Retrieval 使用 FastAPI + Uvicorn；Agent 和 Ingest 是独立队列消费者，有健康检查等 HTTP 需求时再附加接口。

## 1. 共享契约与业务规则

新建 `shared/`，四个服务复用 Pydantic 模型、任务状态和事件类型。共享模块只定义契约，不在导入时加载模型、读取服务密钥或连接数据库。

### 1.1 第一版业务边界

1. 文档按用户私有处理，暂不实现组织共享。所有会话、任务、文档、检索和 trace 查询都校验用户归属。以后引入公共知识库或组织权限时，显式扩展授权范围。
2. 同一会话只允许一个未完成聊天任务，包含排队、执行和等待重试状态；不同会话可以并发。网关通过 MySQL 行锁和会话的 `active_request_id` 原子约束，冲突返回 409。
3. “只检索一次”定义为每个 `request_id` 最多一次成功的逻辑检索，下一次提问可以重新检索。成功结果按请求保存并在任务重试时复用；网络重试可能导致底层检索再次执行，不承诺外部调用恰好一次。不使用 `rag_once:{conversation_id}` 永久禁止后续检索。
4. 第一版最终目标是真正的模型增量输出。联调阶段可以先发送状态和整段答案，但不能把它算作流式生成验收通过。
5. 浏览器断开 SSE 后，已接受的任务继续执行。重新连接只订阅已有任务，不重新提交提问。



### 1.2 消息与接口契约

- `ChatJob`：`schema_version`、`request_id`、`conversation_id`、`user_id`。正文不进队列；Worker 按 `request_id` 查询任务，并核对消息字段与数据库记录一致。
- `IngestJob`：`schema_version`、`job_id`。文件位置、用户、文档版本和任务状态从 MySQL 读取。
- `POST /v1/retrieve`：请求包含 `request_id`、截至本次提问的对话消息和 `search_query`；响应包含检索状态、父文档列表、`parent_id`、`document_id`、`version_id` 和来源信息。权限范围由可信身份及数据库任务记录确定，不信任调用方任意提供的用户或文档范围。
- Redis Stream：key 为 `chat:{request_id}`；字段为 `event`（`token` / `status` / `done` / `error`）和 JSON 编码的 `data`。`data` 包含 `request_id`、`attempt` 和事件内容；token 是增量文本。SSE 的 `id` 使用 Redis Stream entry ID。
- 新执行尝试先发送 `status`，包含 `phase=started`、新的 `attempt` 和 `reset=true`，客户端清空上一尝试的临时答案。`done` 表示答案已经提交 MySQL；`error` 仅表示不可恢复或重试耗尽后的最终失败。
- 创建聊天任务与订阅事件分开：`POST /v1/chat` 返回 202、`request_id` 和事件地址；`GET /v1/chat/{request_id}/events` 提供 SSE；`GET /v1/chat/{request_id}` 返回持久化状态及成功后的完整答案。



## 2. 基础设施与服务配置

1. 在 `deploy/docker-compose.yml` 启动 MySQL 8、Redis 7、RabbitMQ、Qdrant。固定经过验证的具体镜像版本，端口、账号和连接配置从环境变量读取，提交 `.env.example`，不提交实际密钥。
2. 为数据库、向量库和 RabbitMQ 配置持久化卷，配置健康检查与重启策略。容器化应用使用 `depends_on: service_healthy` 等待依赖；本机 Python 服务自行检查就绪并实现运行期间重连。单机重启策略不等于高可用，数据卷不替代备份。
3. RabbitMQ 声明持久化交换机、`chat.requests`、`ingest.jobs` 及各自死信交换机和死信队列，明确绑定关系。消息持久化、发布端开启 publisher confirms 并处理不可路由返回，消费端手动 ACK。
4. Qdrant 建立 `hybrid_collection`，保留 `dense_vector`、`sparse_vector` 命名以及现有模型对应的维度和距离配置。记录 Embedding、Sparse、Reranker 模型版本与切分配置，避免入库和查询使用不同配置。
5. `core/config.py` 只在各服务启动时校验自己的配置，不在 import 时强制要求模型密钥。Agent 和 Retrieval 均需要模型 API 配置，因为 Rewrite / HyDE 仍留在 Retrieval；Ingest 不需要生成模型密钥。
6. 本机进程通过宿主机映射端口连接中间件；未来容器内进程通过服务名连接。中间件开发端口绑定本机，网关是唯一面向浏览器的业务服务。
7. 配置统一上传根目录和模型缓存目录。开发时网关与 Ingest 共享本地目录；容器化后挂载同一目录或数据卷。数据库保存相对文件标识，由各进程在上传根目录下解析，不能依赖用户电脑上的绝对路径。
8. 固定 Python 依赖版本；模型和数据库客户端改为服务启动时初始化、退出时关闭，避免导入工具注册模块就加载整套检索模型。



## 3. MySQL、可靠投递与任务恢复

第二阶段已启动中间件并建立 RabbitMQ 队列、Qdrant 集合。本阶段先分别实现 MySQL、RabbitMQ、Redis 的运行时能力，再由应用编排把它们连接起来。组件只负责自身的连接、读写与错误反馈；跨组件的事务、投递、重试和恢复规则由应用层决定。MySQL 保存业务事实，RabbitMQ 传递待执行任务，Redis Stream 传递可过期的实时事件。

### 3.1 MySQL：保存事实与控制并发

1. 使用 SQLAlchemy 2 异步会话和 Alembic 管理业务表结构。每个请求或任务使用独立会话，不在并发协程间共享会话；事务由业务用例控制，数据访问操作不自行提交。Compose 首次启动只创建数据库和账号，业务表由迁移建立。
2. 建立用户、会话、消息、聊天任务、文档、文档版本、父块、入库任务、检索记录和 outbox 事件的持久化模型。父块正文存入 MySQL，替代 `docstore.json`；检索记录保存输入、成功结果、来源版本与 trace，按用户授权访问。处理中或失败的文档版本不可检索。
3. 用数据库约束兜住重复写入：邮箱唯一、会话内消息序号唯一、同一请求的 user/assistant 消息各至多一条；提交幂等键在用户范围内唯一。同键同内容返回原任务，同键不同内容返回冲突。同一会话通过行锁与 `active_request_id` 保证至多一个未完成聊天任务，并在受理时固定历史截止序号。
4. 聊天和入库任务统一使用 `pending` / `running` / `retry_wait` / `succeeded` / `failed`；保存执行次数、错误、下次可执行时间和租约信息。成功与最终失败是终态。任务状态、完整答案及文档发布状态以 MySQL 为准。
5. Outbox 事件保存唯一事件 ID、目标、业务 ID、payload、`available_at`、发送状态与重试信息。用原子领取和发布租约支持多个发布实例；任务领取、续租及完成写入也使用条件更新，让旧执行者失去租约后无法覆盖新结果。



### 3.2 RabbitMQ：可靠传递工作通知

1. 沿用第二阶段建立的 `chat.requests`、`ingest.jobs` 和死信拓扑，补齐运行时的连接、持久化发布、publisher confirms、不可路由返回、消费并发控制和手动 ACK。队列消息只携带版本及任务标识等必要字段；Worker 按标识到 MySQL 读取正文、权限和当前状态。
2. RabbitMQ 至少一次投递，因此重复消息是正常情况。Worker 先在 MySQL 原子领取任务；已完成、尚未到重试时间或由其他有效租约持有的任务，不再次执行。成功或已持久化的重试安排提交后 ACK；最终失败持久化后可 `nack(requeue=false)` 进入死信队列，供排查和受控重放。
3. MySQL 不可用、结果未提交或重试安排未持久化时，不提前 ACK。停机时先停止领取新消息，再等待或安全中止在途任务。死信队列是故障线索，不能替代 MySQL 中的任务状态。



### 3.3 Redis：短期事件与实时回流

1. 提供运行时连接与 Stream 读写能力，按第 1 节契约向 `chat:{request_id}` 写入 `status`、`token`、`done`、`error` 事件。保持事件 ID 可用于 SSE 续读；活动流保留完整事件，终态后设置保留期。模型增量 token 的产生留给第 6 阶段。
2. `done` 只在完整答案与成功状态提交 MySQL 后写入，`error` 只用于最终失败；终态事件从 MySQL 的 outbox 发布。Redis 写入失败时继续重试；Stream 过期或丢失时，网关可从 MySQL 查询状态与完整答案。重复终态事件由接收端按请求和终态幂等处理。



### 3.4 应用编排：把三项能力串成可靠流程

1. **受理任务**：在一个 MySQL 事务中创建用户消息、聊天任务并占用会话，同时写入投递 RabbitMQ 的 outbox；上传则创建文档版本、入库任务及 outbox。事务提交后返回 202，表示任务已可靠记录，不表示消息已发布或处理已完成。
2. **发布 outbox**：独立发布循环领取到期事件。RabbitMQ 任务消息收到 confirm 且确认没有路由失败后，或 Redis 终态事件 `XADD` 成功后，才标记事件已发送。发布失败记录原因并退避重试。发送成功但尚未标记时进程退出，可能造成重复发布，因此不能假设跨系统恰好一次。
3. **执行任务**：Worker 收到消息后通过 MySQL 条件更新领取任务，记录 `attempt`、租约拥有者与到期时间，并在执行期间续租。实际 Agent 生成和文档入库分别在第 6、4 阶段接入；本阶段先用可控的任务处理逻辑验证领取、提交和确认边界。
4. **处理失败**：暂时性错误在一个事务中改为 `retry_wait`、设置有上限的退避时间并写入新的 outbox，提交后 ACK 当前消息；参数错误、坏文档及重试耗尽进入 `failed`。成功和最终失败时原子释放聊天会话的 `active_request_id`，并写入 Redis 终态 outbox。不能用无限立即重新入队代替持久化重试。
5. **恢复过期任务**：恢复循环扫描租约过期的 `running` 任务，将其重新安排执行或转为最终失败，并在同一事务中写入相应 outbox。旧执行者发现续租失败应停止；所有结果写入都核对当前 `attempt` 和租约。任务最大时长、消费确认超时、心跳、租约及重试次数统一配置。



### 3.5 用一条请求验证边界

用户在会话中提交“根据员工手册，我有多少天年假？”：受理事务写入 user 消息、`pending` 任务和 outbox；发布循环确认 RabbitMQ 收到任务；Worker 原子领取后把任务改为 `running`。若处理时临时失败，事务记录 `retry_wait` 和延迟投递事件，提交后 ACK；下一次执行成功时，将完整回答、`succeeded` 状态、会话释放和 `done` outbox 一起提交，之后才 ACK。发布循环再把 `done` 写入 Redis Stream，网关推送给浏览器。重复投递不应重复生成答案；Redis 不可用时，MySQL 中的完整答案仍可查询。

按三层分别验收：先确认 MySQL 事务、唯一约束与租约竞争；再确认 RabbitMQ 发布确认、重复投递与 ACK/死信；再确认 Redis Stream 读写与过期；最后注入发布后崩溃、Worker 租约过期和 Redis 写入失败，验证 outbox、幂等和恢复流程。并发与行锁测试使用真实 MySQL。

## 4. 最小入库与旧数据迁移

先准备稳定检索数据，再实现 Retrieval 服务。将 `services/ingest/document_loader.py` 和 `services/ingest/create_database.py` 收成 Ingest 消费者，第一步先打通单份 Markdown。

### 4.1 幂等入库与版本发布

1. 消费 `ingest.jobs`，按任务领取规则进入 `running`，只处理该 `job_id` 对应的文件。去掉 `D:\advanced_RAG\data\raw_md` 等硬编码路径；转换失败要显式返回错误。
2. 沿用现有切分和 FastEmbed，但为文档版本、父块和子块确定稳定 ID，例如由 `version_id + 块序号` 派生。相同任务重试复用同一版本、同一切分结果或固定配置，不重新随机生成全部 UUID。
3. 父块先幂等写入 MySQL 的处理中版本，再将子块 upsert 到 Qdrant。payload 至少包含 `user_id`、`document_id`、`version_id`、`parent_id`；创建过滤需要的 payload 索引。
4. 等待向量写入完成并校验该版本预期块数后，在 MySQL 事务内将版本发布、更新文档当前版本、将任务标记成功，再 ACK。该事务是版本对查询可见的切换点。
5. 部分失败的版本保持不可见，重试可以重复 upsert。不可恢复失败记录原因，提供仅针对该版本的残留清理流程。新版本发布前旧版本仍可查询，发布后按保留策略清理旧版本，不能提前删除可用数据。
6. MySQL 与 Qdrant 没有共同事务，以上依靠“版本不可见 → 完整写入 → 发布”的流程保证读取边界。Retrieval 必须按 MySQL 已发布版本集合过滤，并在取正文时再次检查。



### 4.2 迁移与固定基线

1. 在修改旧数据前确认备份或实际可用的数据来源，导出本地 Qdrant 点、向量和 payload，以及 `docstore.json`；缺失时明确记录，不能假定仍存在。停写后迁移，避免读取变化中的本地库。
2. 迁移已有数据时保留原 `parent_id` 和 point ID，补充文档、版本及归属信息，再写入 Qdrant Server 和 MySQL。旧资料没有用户信息时，显式配置归属用户；来源文件名有歧义时建立映射，不能静默合并或默认公开。
3. 校验父块数、向量点数、向量配置和引用关系，确认不存在指向缺失父块的点，再发布迁移版本。
4. 没有旧数据时，用固定文档建立新基线并生成 ID 映射。重新切分或重新生成 ID 的数据按来源和正文内容比较，不要求新旧 UUID 相等。
5. 保存固定问题、检索输入及预期来源作为回归集。隔离 LLM 改写波动进行检索基线对比，再单独验证端到端效果。



## 5. Retrieval 服务

保留 Rewrite / HyDE、Dense、Sparse、父块映射、RRF、Rerank 算法流程，改造执行方式、存储和权限边界。

第五阶段的代码阅读顺序、逐步数据流与验收命令见 [Retrieval 实现说明](05-Retrieval.md)。

1. 用 FastAPI + Uvicorn 提供 `POST /v1/retrieve`。内部调用使用专用服务凭据，校验签名、有效期和 audience，再按 `request_id` 查询任务及用户；不能把“服务凭据有效”等同于“可以访问任意文档”。
2. 从 MySQL 获取该用户有权访问的已发布版本集合，Dense 和所有 Sparse 查询都带相同过滤。不得先跨用户全库召回、再把结果送入模型后才过滤。读取父块正文时再次核对用户、版本和发布状态。
3. `qdrant_shared.py` 改用连接 Qdrant Server 的 `AsyncQdrantClient`，网络调用使用 await；改用 URL 的同步客户端本身不会变成异步。
4. Embedding、Sparse 编码、Reranker 是本地同步计算，放入受限执行器或独立计算进程，按库的线程安全性和 CPU/GPU 资源确定方式。限制在途请求和推理并发，避免在事件循环内直接运行。模型启动时加载，不能盲目增加 Uvicorn Worker 导致重复占满内存或显存。
5. 修正现有先 await Dense、再 gather Sparse 的顺序：在计算和 I/O 已隔离且资源允许的前提下，同时调度两路，收齐结果后做融合。设置调用超时和取消处理。
6. `fetch_parent_docs_by_ids` 改为异步批量查询 `parent_chunks`，保留 RRF 顺序和来源，不再读取本地 JSON。
7. 按 `request_id` 保存成功的检索结果和 trace；同一请求的重复调用复用结果，并核对输入一致。失败不记为“已成功检索”。返回给 Agent 的内容继续遵守原工具结果 JSON 契约。
8. 用固定数据验收召回、用户隔离、版本过滤、超时和多请求响应能力，通过后再接入 Agent。



## 6. Agent Worker 与流式事件

第六阶段的文件阅读顺序、事务边界、重试数据流与验收命令见 [Agent Worker 实现说明](06-Agent.md)。

1. 用 `aio-pika` 消费 `chat.requests`，按任务状态原子领取。第一版每个进程业务并发设为 1～2，配合小 Prefetch 和显式并发限制；Prefetch 不替代会话约束。
2. 按 `chat_requests` 的 user 消息 ID 和历史截止序号读取上下文，不能只按 `conversation_id` 读取执行时的全部消息。组装 system 和历史消息时明确失败轮次的处理规则，避免将后续提问混入旧任务。
3. 保留 RAG 工具 schema，将工具执行改为调用 Retrieval HTTP 接口。解除 `services/agent/tools/` 对检索实现和模型的导入依赖；复用异步 HTTP 客户端，明确超时和可重试错误。
4. 请求内已有成功检索结果时加载并复用，恢复原有 tool message 格式；下一次提问是新的 `request_id`，可以重新检索。不要只保存布尔值却丢弃参考资料。
5. 改造 `run_agent_async` 为输出结构化业务事件，由网关编码 SSE，避免业务层传递嵌套的 `data:` 字符串。模型调用开启流式输出，正确累计工具调用 ID、名称和分片参数，待参数完整后执行工具；只向浏览器发送可展示的答案增量及业务状态，不把工具参数或内部推理内容作为答案。
6. 每个 attempt 开始先写 reset 状态，再将 token/status 写入 `chat:{request_id}`；前端按 attempt 隔离重试输出，丢弃旧 attempt 事件。应用同时累计本次完整答案。
7. 完成顺序固定为：提交完整回答、任务成功状态、会话释放和终态 outbox → 发布 `done` → ACK。`done` 发布失败时由 outbox 补发；终态已可靠提交后可 ACK，重新投递只补通知，不重新调用模型。终态事件允许重复通知，客户端按请求终态幂等处理。
8. 暂时性失败按共享规则安排重试，并发送非终态 status；最终失败先持久化错误和终态 outbox，再发送 error，并按死信规则处理。模型流中途失败后，新 attempt 必须先 reset，不能直接把重试答案接到旧文本后。
9. Redis 不可用时不能依赖 error 事件报告故障：MySQL 仍记录最终状态，网关查询接口提供恢复路径。设置生成时限和输出大小限制；活动流保留完整事件并续期，终态后设置可配置保留期，不在活动期间随意裁剪前缀。



## 7. 网关与 SSE 恢复

网关只依赖共享契约、MySQL、Redis 和发布基础设施，不导入 Agent、检索或入库实现。

1. 注册登录使用密码哈希，签发短期 access JWT。refresh token 使用可撤销的 Redis 记录和轮换机制，浏览器通过 HttpOnly Cookie 持有；配置适当的 SameSite、生产 HTTPS/Secure 和刷新接口来源校验。提供刷新和退出接口。
2. 提供会话创建、列表、历史查询接口，统一检查用户归属。所有接收资源 ID 的接口都做归属校验，包括聊天状态、SSE、上传任务状态和 trace。
3. `POST /v1/chat` 校验 JWT、参数和会话归属，按用户原子限流。使用客户端幂等键，按第 3 节事务创建任务和 outbox，返回 202。重复网络提交返回已有 request，不新增 user 消息。
4. `GET /v1/chat/{request_id}/events` 将 Redis 事件转换成 SSE。首次从 `0-0` 读取，之后使用上次 entry ID；重连接受 `Last-Event-ID` 或明确的游标参数，不能首次用 `$` 跳过已经生成的事件。前端用 fetch 时自行保存和传递游标。
5. SSE 提供心跳和连接清理。网关定期结合 MySQL 终态判断是否结束，不能无限等待一个可能丢失的 done。Redis 不可用时返回可恢复错误，由前端查询任务状态，而非重新提交问题。
6. Stream 过期或丢失时返回明确的恢复状态：任务成功则从 MySQL 返回完整答案快照，前端替换临时文本；任务仍在执行则转为状态轮询，完成后取完整答案，不拼接缺失前缀的增量文本。重连得到重复终态也不新增气泡。
7. `POST /v1/documents` 检查大小和支持格式，以服务端生成的文件标识写入上传根目录，防止路径越界。临时文件写完后原子落盘，再创建数据库任务与 outbox；数据库失败时清理孤立文件，并提供残留文件核对机制。重试上传使用幂等键避免重复建任务。
8. `GET /v1/ingest-jobs/{job_id}` 查询持久化状态，路径明确表示任务。文档是否可用于检索由后端版本发布规则决定，不依赖前端隐藏按钮。
9. 通过受权限控制的请求 trace 接口向评估程序提供检索状态和 `retrieved_parent_ids`，常规聊天响应不必附带完整内部 trace。



## 8. 前端

Vite + React，只请求网关。

1. access token 放内存，刷新通过 refresh Cookie 完成；提供登录、退出和刷新失败后的重新登录处理。
2. 从网关读取会话和历史。会话有未完成任务时限制再次提交，同时处理后端 409；刷新页面后根据持久化任务状态恢复界面。
3. 提交消息时生成并保留幂等键，收到 `request_id` 后用 fetch 订阅 SSE。处理跨网络分片的 SSE 帧，保存 entry ID；token 追加到本次 attempt 的气泡，status 展示进度，reset 清空旧 attempt 临时文本。
4. 断线后重连已有 request，不重新 POST 问题。事件不可恢复时轮询任务并用最终完整答案替换临时文本。done/error 的重复通知必须幂等。
5. 上传后轮询入库任务状态，显示重试或失败原因。成功后允许针对新文档提问，但后端仍执行权限和发布状态过滤。



## 9. 验收与回归



### 9.1 正常链路

1. Compose 依赖就绪后执行 Alembic；通过最小入库或迁移得到固定文档，核对 MySQL 父块、Qdrant 点和已发布版本。
2. 直接调用 Retrieval，确认返回已授权、已发布的父块，验证 Dense/Sparse、RRF 和 Rerank 结果。
3. 创建完整聊天任务和 outbox 后投递 `ChatJob`，确认状态、增量 token、完整回答和终态顺序。不能只塞一个数据库中不存在的任务 ID。
4. 经网关注册登录、上传、查询入库状态、提问和重连；确认浏览器在模型完成之前已经收到真实答案增量。
5. `scripts/run_agent_eval.py` 改为提交网关任务、等待结果、读取受控 trace，继续用同一批问题评价父文档召回。迁移保留 ID 时比较 ID；重新入库时使用记录的映射或正文/来源基线。



### 9.2 故障与隔离


| 场景                             | 必须满足的结果                             |
| ------------------------------ | ----------------------------------- |
| MySQL 提交后 RabbitMQ 暂不可用        | 任务不丢失，outbox 恢复后投递，用户可查询 pending 状态 |
| 发布确认后发布程序退出、相同消息重复投递           | 不重复创建答案、文档版本或向量点                    |
| Worker 在结果提交前或 ACK 前退出         | 租约恢复或幂等处理生效；已完成任务不重新生成              |
| 数据库已保存答案但 Redis 写 done 失败      | 终态可补发；状态接口能返回完整答案                   |
| 用户同一会话连续提交或网络重复 POST           | 幂等返回原任务或明确冲突，不混入后续问题、不乱序回答          |
| 模型限流、超时、流中断或坏文件                | 有界重试；重试输出先 reset；最终失败有持久化状态和错误      |
| Qdrant 部分写入后失败                 | 未完成版本不可见；重试使用稳定 ID，无重复点             |
| 用户访问他人任务、SSE、trace 或检索资料       | 请求被拒绝或结果不包含未授权资料                    |
| 新版本处理中或旧版本切换                   | 查询只使用授权的已发布版本，无半份文档                 |
| SSE 首次连接晚于任务开始、重复连接或 Stream 丢失 | 不漏掉可回放事件；无法回放时恢复最终快照，不重复提交任务        |
| 多请求与本地模型推理同时运行                 | 事件循环未被同步计算长期阻塞，内存和推理并发受控            |


各阶段完成后执行对应验收；只有正常链路、故障恢复和原有召回回归均通过，才视为重构完成。
