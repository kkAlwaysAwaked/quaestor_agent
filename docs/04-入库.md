# 第四阶段：最小入库与固定基线

解决任务：**把“一份文档的一个版本入库”变成可以追踪、重试和恢复的后台任务，并明确什么时候这份数据才算完整发布。**

本阶段先打通单份 Markdown。`services/ingest/submission.py` 负责受理与持久化，`services/ingest/worker.py` 负责 Outbox 发布、RabbitMQ 消费、过期任务恢复和状态流转，`services/ingest/create_database.py` 负责固定切分及向量编码，`services/ingest/vector_store.py` 只负责 Qdrant 写入与校验，`infra/mysql/repositories/documents.py` 只负责 MySQL 父块和版本状态。各模块导入时不连接数据库或加载模型。

## 一份文件如何流转

1. 提交入口检查用户和 Markdown 文件，将原文按 `用户/文档/版本.md` 写到统一上传目录。数据库只保存相对 `storage_key`；`resolve_storage_key` 拒绝路径越界。一个 MySQL 事务插入 `documents`、`document_versions(processing)`、`ingest_jobs(pending)` 和入库 Outbox。相同用户、相同幂等键与相同文件返回原任务；同键不同内容报错。
2. Worker 内的发布循环领取 Outbox。RabbitMQ 对持久化消息返回发布确认且没有不可路由退回后，才将 Outbox 标成 `sent`。确认后退出、标记前退出会重复投递，消费者必须能处理。
3. 消费者从 `ingest.jobs` 收到 `schema_version + job_id`，按 ID 查询 MySQL 并条件领取任务：`pending/retry_wait → running`，`attempt + 1`，设置租约。重复消息或未到重试时间的任务不会再次执行。
4. Worker 核对版本配置、用户归属、文件哈希；按标题或长度切父块，再切子块。父块 ID 由 `version_id + parent_index`、子块点 ID 由 `version_id + parent_index + child_index` 确定，同一版本重试不换 ID。先将父块幂等写入 MySQL 的 `processing` 版本，再批量生成 Dense/Sparse 向量并 upsert 到 Qdrant。点 payload 带 `user_id`、`document_id`、`version_id`、`parent_id`。
5. 等 Qdrant 写入确认后，校验该版本的精确点数和全部预期点 ID。最后在同一个 MySQL 事务中把任务改为 `succeeded`、版本改为 `published`、切换文档 `current_version_id`；提交后才 ACK。**这个事务是检索可见性的切换点**。第五阶段的检索必须同时按用户、已发布版本过滤，并在取父块正文时复核。
6. 临时失败写入 `retry_wait`、退避时间和新 Outbox 后 ACK 当前消息；坏文件或重试耗尽写入 `failed`，当前消息进入死信队列。租约过期由恢复循环重排。Worker 续租或最终写入都核对 `owner + attempt + 租约到期时间`，旧执行者不能发布结果。失败版本不进入检索范围。

MySQL 和 Qdrant 不共享事务。Qdrant 先有点、MySQL 版本仍为 `processing` 是允许的中间状态；检索不能以“向量点存在”判断可见。旧已发布版本在新版本处理期间仍可使用。

## 现有数据判断与基线

本仓库的 `qdrant_db/meta.json` 当前为 `{"collections": {}, "aliases": {}}`，`qdrant_db/docstore.json` 不存在；没有可保留 ID 的旧父块或向量点。因此本轮按实现步骤的无旧数据分支，用 `tests/fixtures/employee_handbook.md` 建立固定数据。`scripts/inspect_legacy_ingest.py` 只读盘点旧目录；若其他机器另有旧数据，应先停写、备份并确认归属用户和来源映射，不能直接把没有归属信息的旧点公开导入。

固定回归问题在 `tests/fixtures/retrieval_baseline.json`。入库成功后，`scripts/check_ingest_baseline.py` 会核对 MySQL 父块、Qdrant 点、文件哈希与当前发布版本，并将实际版本、父块 ID 和点到父块的映射写入 `outputs/ingest_baseline.json`。这个输出是运行数据，不提交到仓库；后续 Retrieval 回归可用它校验来源。

## 本机操作顺序

先按 `deploy/README.md` 启动中间件、执行 `python -m scripts.bootstrap_infra` 和 `python -m alembic upgrade head`。随后开两个终端：

```powershell
# 终端一：保持运行；启动时才加载 FastEmbed 模型
python -m services.ingest.worker
```

```powershell
# 终端二：显式指定样本归属用户邮箱，命令打印 user_id 和 ingest_job_id
python -m scripts.inspect_legacy_ingest
python -m scripts.seed_ingest_baseline --user-email learner@example.com
$jobId = "把上一条命令打印的 ingest_job_id 填在这里"
python -m scripts.check_ingest_baseline $jobId
```

样本用户仅用于建立私有归属，密码哈希以 `!` 开头，不可登录。需要重交同一内容时换新的幂等键；固定样本命令用固定键，重复执行返回同一任务。要观察状态，可用 MySQL 查询 `ingest_jobs.status/attempt/last_error`、`document_versions.status`、`documents.current_version_id`、`outbox_events.status`。校验入口会在未完成时明确失败，不会把 `pending` 当成功。

仅在版本已标记 `failed`、并确认旧执行者不再运行后，才可将版本 UUID 作为参数运行 `python -m scripts.cleanup_failed_ingest` 清理该版本的 Qdrant 残留点；它不会清除 MySQL 审计记录或任何已发布版本。

离线检查：`python -m unittest discover -s tests -v`。测试使用 SQLite 和假向量存储，验证确定性 ID、幂等提交、路径安全与版本发布事务；SQLite 不验证 MySQL 行锁，假存储也不验证真实 Qdrant/RabbitMQ。三项中间件启动后仍需执行上述真实链路与故障注入验收。
